# ДЗ 1: архитектура маркетплейса

## Материалы

- [C4 Container-диаграмма](c4-container.md)
- [`service/`](service/) — минимальная реализация одного контейнера из диаграммы

## Домены и зоны ответственности

- **Заказы** — создание заказа, его состав и изменение статуса.
- **Инфраструктура данных** — резервное копирование, миграции и мониторинг хранилищ; это технический, а не бизнес-домен.
- **Каталог** — товары, их описание и связь товаров с продавцами.
- **Платежи** — создание и учёт платежей за заказы, взаимодействие с платёжным провайдером.
- **Пользователи** — учётные записи покупателей и продавцов, их профили и контакты.
- **Рекомендации** — сбор сигналов, формирование и выдача персональной ленты товаров.
- **Уведомления** — отправка пользователю сообщений об изменении статуса заказа.

## Распределение доменов по сервисам

Веб-приложение не владеет доменом: оно даёт покупателю и продавцу единый интерфейс.

| Сервис | Домены | Логика выделения |
| --- | --- | --- |
| Сервис пользователей | Пользователи | Учётные записи, профили и контакты пользователей выделены в отдельную зону ответственности. |
| Сервис каталога | Каталог | Продавцы независимо управляют товарами и их описаниями. |
| Сервис данных рекомендаций | Рекомендации | Принимает события о заказах и данные внешних источников, приводит их к единому виду. |
| Сервис алгоритмических рекомендаций | Рекомендации | Строит выдачу по истории покупок и заданным правилам. |
| ML-сервис рекомендаций | Рекомендации | Хранит и обслуживает модели, которые персонально ранжируют товары. |
| API рекомендаций | Рекомендации | Даёт сайту единый API и объединяет результаты алгоритмического и ML-подходов. |
| Сервис оформления покупки | Заказы, платежи | Заказ и платёж создаются в одном пользовательском сценарии, поэтому на старте они объединены для согласованной обработки. |
| Сервис уведомлений | Уведомления | Отправка сообщений не должна блокировать изменение статуса заказа. |
| Платформа данных | Инфраструктура данных | Администрирует хранилища, но не участвует в обработке бизнес-запросов. |

Домен и сервис не связаны правилом «один к одному»: рекомендации разделены между четырьмя сервисами, а заказы и платежи объединены в одном сервисе.

## Владение данными и взаимодействия сервисов

У каждого бизнес-сервиса своё хранилище. Бизнес-сервисы не обращаются напрямую к чужим базам: нужные данные они получают через API или события.

| Сервис | Данные, которыми владеет сервис | Ответственность |
| --- | --- | --- |
| Сервис пользователей | Учётные записи, роли, профили и контакты пользователей | Управляет покупателями и продавцами, предоставляет их данные другим сервисам. |
| Сервис каталога | Товары, описания и связь товаров с продавцами | Позволяет продавцам управлять каталогом. |
| Сервис данных рекомендаций | Нормализованные сигналы о покупках и данные из внешних источников | Собирает и публикует данные для построения рекомендаций. |
| Сервис алгоритмических рекомендаций | Правила выдачи и кэш сформированных рекомендаций | Строит рекомендации на основе истории покупок и правил. |
| ML-сервис рекомендаций | Версии моделей, подготовленные признаки и результаты ранжирования | Обслуживает ML-модель рекомендаций. |
| API рекомендаций | Конфигурация выбора алгоритма и кэш готовой ленты | Возвращает сайту единую персональную выдачу. |
| Сервис оформления покупки | Заказы, позиции заказов, платежи и их статусы | Создаёт заказ и платёж, ведёт их согласованный жизненный цикл. |
| Сервис уведомлений | Уведомления, статусы отправки и попытки доставки | Отправляет пользователю уведомления о заказе. |
| Платформа данных | Конфигурация хранилищ, метаданные миграций, резервных копий и мониторинга | Выполняет обслуживание хранилищ. Не владеет бизнес-данными других сервисов. |

Сервис оформления покупки хранит данные двух доменов в своей базе, потому что оба домена находятся в одном сервисе. Эта база не является разделяемой: другие сервисы к ней не обращаются.

Платформа данных имеет служебный доступ к хранилищам только для миграций, резервного копирования и мониторинга. Она не находится в пути пользовательского запроса: при её недоступности работа уже запущенных сервисов и их БД продолжается, но временно недоступны служебные операции.

| Инициатор | Получатель | Способ | Назначение |
| --- | --- | --- | --- |
| Web-приложение | Сервисы пользователей, каталога, API рекомендаций и оформления покупки | Синхронно, HTTP | Показывает интерфейс, товары, персональную ленту и заказы. |
| API рекомендаций | Сервис алгоритмических рекомендаций и ML-сервис рекомендаций | Синхронно, HTTP | Получает варианты персональной выдачи. |
| Сервис алгоритмических рекомендаций | Сервис каталога | Синхронно, HTTP | Получает данные о товарах для выдачи. |
| Сервис оформления покупки | Сервис пользователей | Синхронно, HTTP | Получает данные покупателя при оформлении заказа. |
| Сервис оформления покупки | Сервис каталога | Синхронно, HTTP | Получает данные о товарах при оформлении заказа. |
| Сервис оформления покупки | Платёжный провайдер | Синхронно, HTTP | Проводит платёж через внешнюю систему. |
| Внешние источники данных | Сервис данных рекомендаций | Синхронно, HTTP/webhook | Передают дополнительные сигналы для рекомендаций. |
| Сервис оформления покупки | Сервис данных рекомендаций | Асинхронно, событие «заказ оформлен» | Передаёт факт покупки для рекомендаций. |
| Сервис данных рекомендаций | Сервис алгоритмических рекомендаций и ML-сервис рекомендаций | Асинхронно, событие | Передаёт нормализованные сигналы о поведении пользователя. |
| Сервис оформления покупки | Сервис уведомлений | Асинхронно, событие «статус заказа изменён» | Запускает отправку уведомления. |
| Сервис уведомлений | Сервис пользователей | Синхронно, HTTP | Получает контакт пользователя для отправки уведомления. |
| Платформа данных | Базы данных сервисов | Асинхронно, служебные задания | Выполняет миграции, резервное копирование и мониторинг вне пользовательских запросов. |

## Альтернативные варианты декомпозиции

### Вариант 1: сервисы по границам ответственности — выбранный вариант

Рекомендации разделены между сервисами сбора данных, алгоритмических рекомендаций, ML-рекомендаций и API. Заказы и платежи объединены в сервисе оформления покупки. Остальные домены выделены в самостоятельные сервисы. У каждого бизнес-сервиса собственная база данных. Этот вариант показан на C4-диаграмме.

**Плюсы:**

- Алгоритмические и ML-рекомендации могут независимо развивать разные команды и масштабировать только нужную часть системы.
- Данные из внешних источников не попадают напрямую в сервисы выдачи: их обрабатывает отдельный сервис данных рекомендаций.
- Заказ и платёж можно согласованно создать в одном сервисе без сетевого вызова между ними.
- Платформа данных не участвует в пользовательских запросах и не становится единой точкой отказа.

**Минусы:**

- Для персональной ленты нужно поддерживать взаимодействие четырёх сервисов рекомендаций.
- Событийный обмен требует мониторинга доставки и обработки повторных событий.
- Нужно поддерживать больше приложений и хранилищ, чем в монолите.

### Вариант 2: модульный монолит

Маркетплейс реализуется одним backend-приложением с модулями пользователей, каталога, рекомендаций, заказов, платежей и уведомлений. Модули вызывают друг друга внутри одного приложения и используют общую базу данных. Внешними остаются платёжный провайдер и источники данных для рекомендаций.

**Плюсы:**

- Один проект, один запуск и одна база данных упрощают разработку, тестирование и развёртывание.
- Модули вызывают друг друга без сетевых запросов.
- Согласованность связанных данных можно обеспечить одной транзакцией базы данных.

**Минусы:**

- Нельзя отдельно масштабировать ML-рекомендации или алгоритмическую выдачу: при росте нагрузки масштабируется всё приложение.
- Изменение или выпуск одного модуля требует выпускать приложение целиком.
- Общая база данных связывает домены и не соответствует требованию целевой архитектуры об отсутствии разделяемых баз данных.

## Финальный выбор

Выбран **вариант 1: сервисы по границам ответственности с отдельными базами данных**.

Этот вариант соответствует требованиям маркетплейса:

- Персональная лента развивается двумя независимыми подходами: алгоритмическим и ML; данные для них изолированно подготавливает отдельный сервис.
- Продавцы управляют товарами через отдельный сервис каталога, не затрагивая оформление покупки.
- Заказы и платежи объединены в одном сервисе, потому что создаются в одном сценарии и требуют согласованного изменения состояния.
- Уведомления запускаются асинхронно и не задерживают изменение статуса заказа.
- У каждого бизнес-сервиса своё хранилище; платформа данных обслуживает их вне пути пользовательских запросов и не владеет их бизнес-данными.

Такое решение сложнее модульного монолита в эксплуатации, но оно даёт отдельным командам возможность независимо развивать рекомендации и изолирует жизненный цикл заказа от каталога и уведомлений.

## Демонстрационный сервис

В рамках задания бизнес-логика намеренно не реализована: сервис отвечает только `200 OK` на `/health`.

### Запуск

Из каталога `homework-01`:

```bash
docker build -t soa-service ./service
docker run --rm -p 8080:8080 soa-service
```

В другом терминале:

```bash
curl -i http://localhost:8080/health
```

Ожидаемый результат:

```text
HTTP/1.0 200 OK
OK
```
